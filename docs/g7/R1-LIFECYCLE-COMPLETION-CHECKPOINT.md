## Architecture finding: clean stop is not offline handoff

The existing Python custodian exclusively creates immutable `supervision/`, holds a lifetime flock, and owns its Node child through an inherited socketpair, pidfd and exact-child waitpid. A clean admin stop combines the actual public Kernel shutdown result with normal exit/reap of that exact Node child. The custodian remains alive, owns the flock and may accept a same-revision start. A CLI cannot infer a custody transfer from that STOPPED reply. Constructor rejection of residue remains unchanged, including after normal custodian death. A1+B1 changes neither that authority nor the stopped-source backup prerequisite.

No admin operation, schema, limit, residue-removal mechanism or release-on-stop shortcut is introduced here. Unknown cleanup remains fenced. Existing admin death/boundary tests remain regressions, not new upgrade qualification.

### Exact remaining handoff prerequisite and minimal proposal

For a new explicitly CLI-owned lifecycle, an authorized implementation can put a coordinator above the custodian from inception: the coordinator owns the actual custodian child, retains the SAME flock description without an unlock window, authenticates the inherited control relationship, seals admission/start, obtains the custodian's clean public-Kernel shutdown plus exact owner-child reap result, and then establishes normal exact custodian-child reap itself before admitting an offline operation. This is a possible continuation of approved stopped/offline CLI semantics, not an assertion that it is implemented. It does not require reopening A1+B1. No arbitrary PID or caller-supplied boolean can substitute for this owned relationship. A durable fence must survive every uncertain/crashed boundary; any eventual residue retirement must occur only within the certified, continuously locked relationship, never during speculative takeover.

The ALREADY detached custodian has no coordinator parent/control capability to receive such a transfer. Retrofitting a release trigger by changing `stop` semantics would silently remove its approved same-custodian restart behavior. Adding a live `release`/`handoff` request would instead require an explicit owner-approved closed operation/schema extension, not an invented fifth admin operation. Minimal conditional owner proposal: approve a separately specified explicit offline-release operation, bound to incarnation and accepted revision, which seals successor admission, requires clean Kernel shutdown and exact owned reaps, transfers the continuously held lock to an authenticated owning coordinator, and retains all fencing on any ambiguity. The exact request/response/ownership/crash contract would need review before implementing that option. This is NOT a pending approval for the already published A1+B1 and NOT a global blocker on G7 development.

Thus generic stopped/offline handoff, detached-custodian exit/reap, stopped-source backup and production replacement transactions are NOT delivered by this checkpoint. No residue was cleared to evade this missing prerequisite.

## Implemented independent capability

`CellPreparation.install()` now performs an exact-reinstall no-op for a supported accepted Cell BEFORE any transaction or persistent trust-floor update:

- The SAME continuously locked object must have completed its own clean public Kernel shutdown. It must have no retained host or running runtime; all journals must be terminal COMMITTED/ABORTED and consistent with accepted selection. A reopened object, no-host `shutdown()`, cached STOPPED reply or readable journal cannot create this permission.
- Existing identity, G7 floor, accepted selection and complete journal chain are validated through the existing status validator. Stored authorization must agree with the separately supplied operator intent and accepted digest.
- Both the entire retained release (including exact inventory/no extras, raw artifact lengths/digests, signatures, profile/lock/package graph and authorization) AND the requested USTAR are inspected against currently valid independently supplied trust. Matching only an archive or accepted manifest digest is insufficient. All selected bundle/profile/lock/policy digests must match the existing accepted release.
- Current signature, expiry/freshness, revocation and G7 clock/version-floor checks remain mandatory. Kernel-owned same-version digest continuity and high-water checks are validated by public Kernel bootstrap against a verbatim private working copy of its opaque state. The production path never parses, rewrites, rolls back or publishes that opaque representation into the Cell. Public bootstrap necessarily persists its own working state, hence using the original state path would violate the no-op requirement. This temporary validation host discovers no packages, issues no grants and starts no providers/calls.
- The validation host must itself complete the existing public clean shutdown checks. Uncertain cleanup retains the host/lock and private diagnostic residue; it is not converted to a successful no-op. The temporary working directory is removed only when no host remains. Original Kernel bytes, final validated status and current trust are checked again before return.
- No accepted replacement, new journal, high-water write, identity/secret reset, activation, replay or custody release occurs. The returned runtime remains STOPPED, not RUNNING. The minimal IPC profile has empty secret/event intents; no new arbitrary secret-storage layout is claimed.

This is deliberately a same-owner component API capability, not a reopened/offline CLI installer. It does not make `stage` an installer or add `install` to live admin. It also does not treat a different valid signed candidate as an upgrade. First installation, activation, fresh grants, readiness and accepted publication keep their existing paths. The existing synchronous-IO/preemption limitation remains: the in-process verification budget is not a hard-real-time guarantee.
