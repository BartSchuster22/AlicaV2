## Delivered path and exact boundary

`python3 tools/g7-owned-coordinator.py run-verify-stopped TRUSTED_NODE ABSOLUTE_INITIALIZED_CELL PRIVATE_INPUTS` is a new foreground CLI-owned lifecycle. It starts custody FROM INCEPTION, performs the existing first installation/readiness in its actual custodian/owner children, seals that lifecycle, establishes clean owned reaps, and performs stopped **read-only release verification** in a separate worker. The operation uses the SAME Cell, its actual accepted release/journals, original input archive and newly read independent private trust/authorization. It does not initialize a replacement Cell to simulate transfer.

The initialized Cell must not have supervision residue. This CLI cannot adopt an arbitrary detached custodian, an already orphaned Cell, or a prior run's stopped fence. It is deliberately not a generic installer/restart command for existing residue. Normal detached custodian `stop`/`start` and v1/v2 administration remain unchanged. The base Supervisor gains only an overridable root acquisition method and a no-op lifecycle tick; detached mode has no new release endpoint.

The CLI parent opens/locks the verified private Cell directory before forking. Its descriptor remains open continuously through the independent custodian's lifetime, clean reap and offline worker. The custodian inherits that SAME open-file description; a separately opened probe must conflict and inode/owner/mode checks must match. The Node owner and read-only worker use the existing native same-description adoption. There is no LOCK_UN or reopen-as-transfer window.

The owned custodian class/captured relationship is minted inside the CLI `run` call, not reconstructed from an argument. CLI/API inputs contain no custodian PID, control path, inherited fd, clean boolean or stored receipt. Its anonymous AF_UNIX SOCK_SEQPACKET pair uses per-message SCM_CREDENTIALS: every parent receipt must come from the actual forked child PID/UID/GID while an exact-child pidfd is held. SO_PEERCRED alone would identify the socketpair creator, not the forked child; it is deliberately NOT used as child authentication. Closed, ancillary-free, truncated and unowned messages fail closed. An unrelated same-UID process/path is not an ownership certificate. Same-UID malicious code/admin replacement remains outside confinement.

The child authenticates GO from its actual parent and arms/rechecks Linux parent-death guarding before Cell effects. The coordinator obtains its exact-child pidfd before GO. Custodian loss kills guarded Node owners; coordinator loss kills its guarded custodian and the separately guarded maintenance worker. The coordinator also arms/rechecks a parent-death guard and holds a pidfd for its CLI parent. These guards contain process loss; they are NOT clean-reap evidence and cannot undo a blocked filesystem syscall.

## Seal and proof ordering

1. Existing public Kernel install/readiness produces the real owner observation. READY is only a private synchronization message, not an offline permit.
2. Coordinator sends SEAL on its own inherited channel, under an unchanged cleanup budget. The custodian atomically latches sealing in its single event loop, unregisters/closes both listeners and closes all previously admitted clients. No start/mutation dispatch is possible after this point. Already-dispatched work is not falsely cancelled; it must finish cleanly within the enclosing seal budget or cause uncertainty.
3. If necessary the custodian drives the existing internal stop path, without changing public stop semantics. The owner must actually complete public Kernel shutdown with existing no-work/no-resources/no-timeout/no-failed-disposer checks. STOPPED selection must match the prior accepted selection.
4. The existing owner pidfd and Popen.poll/waitpid establish normal exit zero of THAT child. Only this real in-memory result can produce CLEAN. The restart permit is consumed and the sealed custodian exits normally without permitting another owner.
5. Coordinator authenticates SEALED then CLEAN, validates the stopped envelope, and uses its held pidfd plus waitpid on its OWN custodian child to establish normal zero exit. A CLEAN message alone, EOF, PID disappearance, timeout or forced kill cannot reach maintenance.
6. Only this lexical success path starts the read-only worker under the continuously retained flock. Its bounded stdout is read nonblocking; its result is accepted only after normal exact worker reap and deadline rechecks. The coordinator compares its accepted sequence/digest to the authenticated stopped selection before reporting success.

Any failure latches NEEDS_OPERATOR, prevents offline success and parks the coordinator retaining its lock. A signal may contain an exact child via pidfd but never certifies cleanup. Parent/coordinator loss leaves the durable supervision fence. No automatic retry, restart, takeover or release-after-uncertainty exists.

## Offline action is verification, not exact reinstall

`tools/g7-stopped-verify.mjs` is a read-only inspector, NOT a clean-permit minting API. It validates existing identity/accepted/journal consistency, terminal transactions, operator authorization, exact retained inventory and signatures, the original supplied archive, and current independent trust against G7 floors. Both inspected release bindings must equal the actual accepted selection. It performs no install/stage/recover/start, no grant issuance and no writes to Cell identity, accepted data, journals or either high-water file. Its direct output is a release inspection result, not STOPPED/clean authority; only its owned coordinator can certify stopped maintenance.

This does NOT revalidate opaque Kernel high-water continuity via the private-copy bootstrap used by the existing exact-reinstall method. That distinct check and the secure cross-process bridge to that method remain implementation work. No new caller-controlled `#stopped` setter/flag or generic channel-to-reinstall shortcut was added. Existing same-object exact reinstall remains intact and is not relabeled independent-process reinstall.

Supervision residue is NEVER retired in this slice, even after success. Consequently there are no residue unlink/rename/fsync retirement transitions to claim qualified. Success closes the coordinator's lock only after normal owned reaps and read-only verification; the durable fence still denies a new coordinator or ordinary Cell constructor. Any future retirement/mutating handoff must stay within a certified relationship and receive separate crash-boundary qualification. No approval blocker is invented: extending exact reinstall/upgrade is an implementation/qualification gap, not a request to reapprove R1/A1+B1.

## Limits and qualifications

All existing schema files/versions/fields/operations and numeric ceilings are unchanged. Control packets use the existing admin frame ceiling. Coordinator initial readiness has an external verification ceiling anchored before GO; the custodian also retains its existing per-phase verification/activation/cleanup budgets. Sealing through custodian reap uses one cleanup budget, started before SEAL; acknowledgements cannot reset it. Read-only verification through worker reap uses one verification budget anchored before worker creation, with elapsed checks after IO, authentication, exact waitpid and decoding. Late receipts/results cannot recreate permission. These are elapsed-time fail-closed checks, not hard-real-time Linux scheduling guarantees. Initial private-root/fence setup still uses synchronous filesystem IO, and OS signals cannot roll back in-flight IO. CLI stdout is diagnostic reporting, not a transferable stopped/reinstall capability; terminal/filesystem delivery latency is not claimed hard-bounded. Live pre-reap Kernel high-water observations may finish during a seal/crash test and must be preserved, not reset. Byte/inode/mtime no-op claims begin only after the actual clean owned reaps.

Execution results, raw failures, process artifacts and exact source/preservation bindings are in the companion execution record and `evidence/g7/owned-coordinator/`. Do not infer every boundary or distinct-UID qualification merely from a passing runner. The development process is UID/GID 1000 with zero effective/permitted capabilities (raw observation retained); no elevated or second-UID executor was used. A distinct-UID negative credential case remains unqualified. The new full-duration verification cases qualify the owned coordinator and its read-only worker, not every detached-custodian verification deadline. Crash injection is process/SIGKILL qualification, not physical power-loss testing. This is a coverage limitation, not an invented owner-approval requirement. No production key, signing, deployment, dependency/toolchain installation, RAM/swap/service change, protected artifact/licensing change, child agent, cron, commit/push or G7/G8 acceptance is included.
